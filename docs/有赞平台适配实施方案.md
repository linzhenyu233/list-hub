## 0. 一句话方案

有赞 = **在 `platform_registry._ADAPTERS` 加一条适配器 + 新建 `youzan/` 服务目录（仿 `xhs/`）+ `bulk_api` 加一个发布处理器**，

## 1. 有赞开放平台基础（开发前必读）

### 1.1 应用类型：选「自用型无容器应用」

| 类型 | 场景 | 凭证 | token 机制 | 本项目建议 |
| --- | --- | --- | --- | --- |
| **自用型（无容器）** | 自己（或服务自己客户）的店铺，做商品/订单同步 | `client_id` / `client_secret` / `kdt_id`（店铺 ID） | `grant_type=silent` 静默换 token，**无 refresh_token**，7 天过期后重新获取 | ✅ **选这个** |
| 工具型（无容器） | SaaS 服务商，给任意商家用 | `client_id` / `client_secret` + 商家授权 code | OAuth，`access_token` + `refresh_token` | ❌ 本项目是自营店铺，不需要 |

要点（官方文档 3031 口径）：
- 一个店铺只能授权给一个自用型应用；**一个自用型应用可绑定多个店铺**（需审核）→ 与本项目「一个 `shop` 一个运营单元」模型天然契合。
- **多店铺 token 以 `kdt_id` 隔离，缓存 key 必须含店铺 ID**，不能跨店复用（与小红书 `tokens/<shop_id>.json` 同思路）。
- token 过期前**1 小时内重复请求返回同一个 token** → 天然幂等，可放心"快到期就重取"。
- 调用有赞 API 前需要在控制台**申请"类目能力包"**（含接口权限），审核一般 1-3 个工作日 → **这是排期唯一的外部阻塞项**。

### 1.2 网关与请求格式

```
POST https://open.youzanyun.com/api/{接口名}/{版本号}?access_token={access_token}
Content-Type: application/json
Body: {业务参数 JSON}
```

- 取 token：`POST https://open.youzanyun.com/auth/token`（表单/JSON 参数见 §1.3）。
- 老域名 `https://open.youzan.com/api/oauthentry/...` 为旧版网关，**新接入统一用 `open.youzanyun.com`**。
- 接口命名规范：`youzan.[业务线].[应用].[动作].[版本]`，例如 `youzan.item.create.3.0.0`。
- **无需签名**：token 模式（`access_token` 放在 query）下不需要 `sign` 参数 —— 与小票的差异点见 §1.4。

### 1.3 返回结构与错误码

| 场景 | 响应壳（★以真机为准，见 §11-★1） |
| --- | --- |
| 取 token 成功 | `{"access_token": "...", "expires_in": 604800, "scope": "..."}` |
| 业务失败（网关层） | `{"gw_err_resp": {"err_code": 4301, "err_msg": "参数类型不匹配"}}` |
| 业务失败（部分接口） | `{"code": 4101, "msg": "请求太频繁"}` |
| 业务成功 | `{"code": 0, "msg": "", "data": {...}}`（部分接口直接返回业务对象） |

已实测/公开确认的错误码：

| 码 | 含义 | 本项目归一化类别 |
| --- | --- | --- |
| `4101` | 请求太频繁 | `RATE_LIMIT` → 退避重试 |
| `4301` | 参数类型不匹配 | `PARAM` → 进失败清单 |
| token 失效类（★码值待核对） | access_token 过期/无效 | `AUTH_EXPIRED` → 重取 token 重试 1 次 |

### 1.4 与现有两平台的机制差异（差异就是坑）

| 维度 | 微信小店 | 小红书 | **有赞** |
| --- | --- | --- | --- |
| 端点风格 | REST 路径 | 单端点 + `method` 参数 | **`/api/{方法}/{版本}` 路径里带 Method** |
| 凭证 | `appid` + `secret` | `app_id` + `app_secret` | **`client_id` + `client_secret` + `kdt_id`** |
| token | 服务自动换（内存缓存） | code 换 token，`tokens/<shop_id>.json`，7 天 + 14 天 refresh | `grant_type=silent`，7 天，**无 refresh_token**，按 `kdt_id` 隔离 |
| 签名 | 无（token 模式） | 有（`md5(method?appId=..&timestamp=..&version=2.0..secret)`） | **无** |
| 价格单位 | 分 | 分 | **元**（`youzan.item.create` 的 `price` 官方注明"单位:元"）★6.1 |
| 商品主图 | 直接传 URL / 文件 → 得 `img_url` | 同上 → `material_id` | **必须先传素材拿到 `image_id`，创建商品只收 `image_ids`** |
| 类目 | 平台类目树 | 平台类目树 + 品牌 | `cid`（★语义见 §6.3，官方文档中"商品分类叶子类目"与社区文章"商品分组/标签"两种说法并存） |
| 商品编码回查 | 商品详情 | `product.getItemInfo` | `youzan.items.custom.get`（按商品编码）/ `youzan.skus.custom.get`（按规格编码） |

## 6. 关键坑与口径（上线前必须逐条确认）

### 6.1 ★★ 价格单位是「分」（最高危）—— 2026-10-15 真机纠正
**早先本文写的是"单位:元"，那是错的**，按那个结论写出来的代码在真机上把商品价格发成了 **1/100**。

现在的结论（两条独立证据一致）：**有赞商品接口的 `price` 一律是「分」**，与微信/小红书相同。
- 证据①（真机）：用户在后台手工建的商品填 **28000 元** → 接口读回 `price=2800000`；
- 证据②（官方）：《有赞云开放接口商品场景对接说明》明确写 `price` **单位：分**；
- 反证（真机事故）：我们曾按"元"发，货盘上架价 699000 元 → 平台存成 **699000 分 = 6990 元**
  （也就是清单价 1/100 卖出去），修正后平台读回 `69900000 分 = 699000.00 元` ✅。

⚠️ 适配器 `price_unit` 必须是 **`cent`**（`platform_registry` 已改），回归测试也钉住了这一条。
⚠️ 订单/退款金额（`ORDER_AMOUNT_UNIT` / `REFUND_AMOUNT_UNIT`）是**另一组字段**，仍未实测（§11-★8）。
- 项目内部统一用「元」，所以适配器 `price_unit="yuan"` 时 `price_to_platform` 返回原值；
- **但订单/退款金额的单位必须单独实测**（`ORDER_AMOUNT_UNIT` / `REFUND_AMOUNT_UNIT`），有赞不同接口存在"元/分"混用可能；
- 上线前**人工核对平台后台价格**一次（对齐《新平台适配层实施方案》§5.3）。
- 若写成 `cent`：不会报错，只会**超低价卖出**。

### 6.2 图片必须"先传素材，再引用 `image_id`"
`youzan.item.create` 的 `image_ids` 只接受有赞素材 ID（逗号分隔，≤15 张），**不接受外链 URL**。
所以 `_platform_image()` 的外链/本地两条路径都要落到 `/materials/upload`，返回 `image_id` 后再进 payload —— 与微信/小红书"直接给 URL"不同，**顺序不能省**。

### 6.3 `cid` 的语义要在真机确认
官方《商品场景》说 `cid` 是"商品分类的叶子类目 id"（`youzan.itemcategories.get` 获取）；
开发者社区文章又说"此处的 `cid` 也就是商品分组 id，也叫商品标签 id"。
→ 实施时用 API 调试工具拿真实 `itemcategories.get` 返回，**看树结构再定映射策略**（项目 `category_aliases.youzan_json` 存的就是它）。

### 6.4 发布必填项比微信多
有赞 `item.create` 已知必填：`title`、`desc`（>5 且 <25000 字符）、`image_ids`、`price`、`quantity`/`sku_stocks`、`cid`。
→ `desc` 项目现有货盘没有现成字段，建议**用标题 + 固定模板合成**（`_youzan_payload` 内生成，不入库）；
→ 这些必填项要在 **payload 前置校验**（仿 `_missing_shop_params`），不要等平台报 4301。

### 6.5 SKU 结构差异
有赞 SKU 随 `youzan.item.create` 一起创建（`sku_stocks` 一类数组，含价格/库存/规格编码，★字段名以官方文档为准），
改价用 `youzan.item.sku.update`、改库存用 `youzan.item.quantity.update`（**该接口不能改价**）。
→ `sku_id` 回填用创建响应里的规格 ID；`sku_image_fallback=True`（每个规格都要图，缺则用主图）。

### 6.6 订单同步节奏
- 主动查询有延时：**交易后 30 秒以上再查**；列表为空可重试；
- 时间窗与分页参数 ★待核对（4.0.4 详情页）；
- 面板要拿「商品维度拆解」需订单详情里的 `order_items`，字段名 ★核对。

### 6.7 限流
`4101 请求太频繁` 已确认。有赞对调用频率敏感，`rate_limit_markers=("4101", "请求太频繁")` 命中后由 `mock_platform.gateway_call` 指数退避重试。
另外**Worker 总线程数**会因第三个平台上升到 `店数 × 3 × 6`，必要时把 `BULK_WORKERS_PER_SHOP` 降到 3。

### 6.8 标题重名（继承现有问题，本次不解决）
微信侧 250 个商品里已有约 151 个因重名失败；有赞同样会以"商品名称重复"类错误拒绝。
→ 沿用现有决策（见 `huopai_adapter.py` `enrich_titles` 上方「待办」注释）：**先发，只修被拒的**，或按运营决策加回克拉/净度/镶嵌方式。

### 6.9 token 无 refresh_token
自用型 `grant_type=silent` 直接重取，**不要照抄小红书的 `refreshToken` 逻辑**（有赞返回里没有）。
"剩余 <1 小时自动重取" + "1 小时内重复请求返回同一 token" 组合起来最稳。

| 8 | 订单只读 | 能用订单号在 `/orders` + `/order-detail` 取到，金额单位与后台一致 |
| 9 | 失败清单 | 故意错参数 → 有赞错误码/文案可读、可改后重试 |
| 10 | 反向验证 | 微信/小红书发布状态**未**被污染（跨店/跨平台隔离） |

## 10. 风险与应对

| # | 风险 | 影响 | 应对 |
| --- | --- | --- | --- |
| Y-R1 | **类目能力包审核不通过/延迟**（含订单、商品权限点） | Y5 无法开始 | Y1-Y4 全部做成"无凭证可交付"；能力包按 `supports` 声明，未批的能力直接隐藏不出页 |
| Y-R2 | **价格单位元/分搞错** | 超低价卖出，资金损失 | 适配器 `price_unit="yuan"` + 单测 + §9-5 人工核对 + 代码审查必查项 |
| Y-R3 | 订单/退款金额单位与商品价格单位不一致 | 面板数据算错（但不会造成资金损失） | `ORDER_AMOUNT_UNIT` / `REFUND_AMOUNT_UNIT` 分开配置，真机对一次账 |
| Y-R4 | ★字段名/接口名与本文档不一致 | 联调期返工 | 所有 ★ 项**先核对再写代码**（§11），且全部收敛在 `youzan_store.API_MAP` 常量区 |
| Y-R5 | 发布必填项（`cid`/`desc`/`image_ids`）缺失 | 平台直接拒单 | `_youzan_payload` 前置校验，不落到平台才失败 |
| Y-R6 | 第三个平台把 Worker 线程数推高触发限流 | 三个平台失败率同时上升 | 上线前重算 `店 × 平台 × BULK_WORKERS_PER_SHOP`，必要时降至 3；观察 `4101` 出现频率 |
| Y-R7 | 标题重名导致大批失败 | 失败清单膨胀 | 沿用现有标题策略决策（§6.8），不因接有赞而改变口径 |
| Y-R8 | 串店（A 店商品发到 B 店） | 最高危 | 复用现有隔离机制并**追加有赞跨店回归用例**（`multishop_regression_test.py`） |
| Y-R9 | `_order_api_base()` 等硬编码未改 | 有赞订单打到小红书服务 | §5.4 全部改完并加断言 |
| Y-R10 | mock 数据被当成真实发布 | 运营误判 | 复用 `publish_items.mode` 机制，前端显示「模拟」标记 |
