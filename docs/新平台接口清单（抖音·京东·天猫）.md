## 0. 阅读说明（务必先读）

### 0.1 本清单的定位

三个平台目前**卡在软著证书上**，意味着：应用入驻审核未通过 → 权限点未开通 → 官方文档中的接口清单、
沙箱环境、错误码表**都拿不到全量**。因此本清单的作用**不是替代官方文档**，而是：

1. 提前把**中台侧需要产出的数据契约**固定下来（谁填什么、什么必填），让业务代码可以先写；
2. 把**平台差异点**（签名、token 生命周期、字段语义、错误码归一化）列清楚，接新平台时只需补
   `store` 客户端的实现，不动编排层；
3. 给出**联调前必须逐字核对**的清单（带 `*` 的项），避免上线后才发现字段名不对。

### 0.2 标记规则

| 标记 | 含义 | 处理方式 |
| --- | --- | --- |
| 无标记 | 接口名 / 参数名来自公开且稳定的文档 | 直接实现 |
| `*` | 接口名、参数名或必填性与平台版本相关，必须在拿到官方文档后逐字核对 | 收敛到 `API_MAP` 常量，改一处即可 |

> 带 `*` 的项**不要**散落在业务代码里，一律写进各平台 `xxx_store.py` 顶部常量区，联调时只改这一处。

### 0.3 三个平台与现有两个平台的本质差异

| 维度 | 微信小店（已接） | 小红书（已接） | 抖音（抖店） | 京东（POP 商家） | 天猫（淘宝开放平台） |
| --- | --- | --- | --- | --- | --- |
| 网关形态 | 多路径 REST | 单网关 + `method` 分发 | 单网关 + `method` 路径 | 单网关 + `method` 参数 | 单网关 + `method` 参数 |
| 业务参数位置 | body | body 平铺 | `param_json` JSON 串 | `360buy_param_json` JSON 串 | 平铺 query/form |
| 签名 | 无签名 | MD5 | MD5 / HMAC-SHA256 `*` | MD5（大写） | MD5（大写）/ HMAC `*` |
| 凭证 | `access_token` | `accessToken` | `access_token` | `access_token` | `session`（字段名不同！） |
| token 生命周期 | 2h 自动续 | 7 天 / 14 天 | 7 天 / 30 天 `*` | 约 1 年 `*` | 约 1 年（长期授权）`*` |
| 是否有沙箱 | 无（用测试店） | 无（测试店铺） | 无通用沙箱 `*` | 有测试环境 `*` | 有沙箱 `*` |
| 商品创建模式 | 商品 + SKU 一体 | 商品与 SKU 分两步 | 商品 + SKU 一体 | 商品与 SKU 分开 | 商品与 SKU 分开 |
| 价格单位 | **分** | **分** | **分** | **元** `*` | **元** |
| 上下架 | 独立接口 | 独立接口 | 编辑时改状态 `*` | 独立接口 `*` | 独立接口 |

> 价格单位是最容易踩的坑：微信/小红书/抖店用「分」，京东/天猫用「元」。
> 中台内部统一用**元**（`_wechat_payload` 里 `*100` 就是这一层转换），适配层负责换算。

### 0.4 中台侧「规范模型」——所有平台的共同入参来源

清单里反复出现的「规范模型」，指的就是中台已有的商品字典（见 `bulk_api/bulk_api.py:_wechat_payload`
`_xhs_payload`、`huopai_adapter.py` 转换输出），**新平台不新造模型**：

```python
product = {
    "product_code": "ZSTZ106JR-15",     # 商家编码，即平台的 out_product_id/outer_id
    "title": "...",                     # 基础标题
    "wechat_title": "...",              # 平台标题列（新平台要各加一列）
    "xhs_title": "...",
    "internal_category": "培育钻-戒指",   # 内部类目，映射到平台叶子类目
    "attributes": {"材质": "18K金", ...},# 平台属性（attr_key/attr_value 形态）
    "weight": 3.2,                      # 克重
    "main_images": ["https://...jpg"],  # 主图（已上传到该平台素材空间的 URL）
    "detail_images": ["https://..."],
    "description": "<html>...",
    "skus": [{
        "sku_code": "...", "price": 1999.0, "original_price": 2599.0, "stock": 10,
        "specs": [{"name": "戒托颜色", "value": "白色"}],
        "uploaded_sku_image": "https://...",
    }],
}
```

**结论：三个新平台的商品类接口，入参全部来自上面这个字典 + 店铺私有参数（品牌/类目/运费模板/售后地址）。**
这正是适配层能做成「插件」的前提。

| 项 | 抖音（抖店） | 京东（POP） | 天猫 |

| 每店一套凭证 | 是 | 是 | 是 |

> 抖音权限点分散、需逐项申请 → 中间做，但要提前把权限点清单报给运营去申请。

## 2. 抖音（抖店开放平台）

### 2.1 框架层：网关 / 签名 / 授权

| 项 | 值 |
| --- | --- |
| 正式网关 | `https://openapi-fxg.jinritemai.com` |
| 鉴权网关 | `https://openapi-fxg.jinritemai.com/token/create`、`/token/refresh` |
| 请求方式 | 业务参数 POST；公共参数可在 query，也可放 body `*` |
| 公共参数 | `app_key`、`method`、`param_json`、`timestamp`（`yyyy-MM-dd HH:mm:ss`）、`v`、`sign`、`sign_method`（`md5` / `hmac-sha256`）`*` |
| 业务参数 | 全部 JSON 序列化后放进 `param_json`（**不是平铺**，与小红书不同） |
| 签名规则 | 公共参数 + `param_json` **整体作为一个值**参与排序拼接，按 key 升序 `k=v` 连接，首尾拼 `app_secret`，MD5；大小写以官方签名工具为准 `*` |
| 响应壳 | `{"data": {...}, "err_no": 0, "err_tips": "success"}`；部分新版接口为 `{"code","message","data"}` `*` |
| 限流 | 按 `app_key` + 接口维度 QPS 限制 `*`；批量任务必须带退避重试 |

#### D-A1 `token.create` — 用授权 code 换 token

| 入参 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `code` | string | 是 | 店铺授权回调里的 code，**短时效（分钟级）** |
| `grant_type` | string | 否 | 固定 `authorization_code` |

| 出参 | 类型 | 说明 |
| --- | --- | --- |
| `access_token` | string | 业务接口凭证，有效期 7 天 `*` |
| `refresh_token` | string | 续期凭证，有效期 30 天 `*` |
| `expires_in` | number | 秒 |
| `scope` | string | 授权的权限点集合 |

#### D-A2 `token.refresh` — 续期

| 入参 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `refresh_token` | string | 是 | 上一步拿到的 |
| `grant_type` | string | 否 | 固定 `refresh_token` |

出参同上（新的 token 对）。**规则：refresh_token 30 天内至少用一次，否则必须重新授权**
——与小红书的 7/14 天规则同构，可直接复用 `xhs/tokens/<shop_id>.json` 那套落盘+续期逻辑。

### 2.5 数据统计

| 接口 | 功能 | 关键入参 | 关键出参 | 备注 |
| --- | --- | --- | --- | --- |
| 店铺数据总览 `*` | 核心指标（成交额/订单量/访客） | `start_date`、`end_date` | 指标数组 | 多为 T+1 数据 |
| 商品数据 `*` | 单品维度指标 | `product_id`、时间区间 | 曝光/点击/成交 | 单次查询商品数有上限 |
| 流量/转化数据 `*` | 店铺流量漏斗 | 时间区间、维度 | 指标数组 | 部分能力仅后台可见，开放接口可能不提供 `*` |

> **重要提醒**：数据类接口在三个平台的**开放程度差异极大**，且普遍有 T+1 延迟、
> 单次查询时间跨度上限、指标上限。方案里把这部分排在 P2，并且**先用「本地发布记录 + 平台订单拉取」
> 自算基础看板**，不依赖平台的统计接口（详见实施方案 §3 优先级表）。

| 接口 | 功能 | 关键入参 | 关键出参 | 备注 |
| --- | --- | --- | --- | --- |

> 营销模块的实际情况是：**三个平台都不把营销完整开放给自研应用**。
> 务实的做法是只做「查询已有活动 + 读券效果」这类只读能力，
> **不做写操作**（写错了直接影响店铺资金/活动资格，风险极高）。

### 2.7 抖音错误码

| 层级 | 码 | 含义 | 中台归一化 |
| --- | --- | --- | --- |
| 框架 | 系统繁忙 / 5xx `*` | 平台侧异常 | `SYSTEM` → 重试 |
| 框架 | 签名错误 `*` | sign 计算与服务端不一致 | `AUTH` → 不重试，告警 |
| 框架 | token 失效 / 过期 `*` | 需 refresh 或重新授权 | `AUTH_EXPIRED` → 自动 refresh 后重试 1 次 |
| 框架 | 权限点未开通 `*` | 应用没申请该接口权限 | `PERMISSION` → 提示运营去申请 |
| 框架 | 流控 `*` | QPS 超限 | `RATE_LIMIT` → 指数退避重试 |
| 业务 | 类目/属性非法 `*` | 叶子类目与属性不匹配 | `PARAM` → 单向失败，进失败清单 |
| 业务 | 商品不存在 / 已删除 `*` | 回查时 404 | `GONE` → 与现有 `_WECHAT_GONE_MARKERS` 同语义 |
| 业务 | 价格/库存非法 `*` | 超范围 | `PARAM` |

> 抖音业务错误码量大（数百个），**不要试图在代码里穷举**。
> 适配层只做 `(平台 err_no) → 6 类归一化` 的映射表，全表在联调期从官方错误码文档导出成
> `douyin/error_codes.json`，未命中的落 `UNKNOWN` 并保留原始 `err_no`/`err_tips` 原文。

## 3. 京东（POP 商家开放平台）

### 3.1 框架层：网关 / 签名 / 授权

| 项 | 值 |
| --- | --- |
| 业务网关 | `https://router.jd.com/api`（商家自研）；另有 `https://api.jd.com/routerjson` `*` |
| 授权网关 | `https://oauth.jd.com/oauth/token`（OAuth2.0 标准） |
| 请求方式 | POST（`application/x-www-form-urlencoded`） |
| 公共参数 | `method`、`app_key`、`access_token`、`timestamp`（`yyyy-MM-dd HH:mm:ss`）、`format=json`、`v=2.0`、`sign_method=md5`、`sign` |
| 业务参数 | 全部 JSON 序列化后放进 `360buy_param_json`（**注意字段名不是 param_json**） |
| 签名规则 | 按 key 升序排，拼 `key + value`（**不含 `=` 和 `&`**），首尾拼 `app_secret`，MD5 后转**大写**；`360buy_param_json` 作为整体一个值参与 |
| 响应壳 | 成功：`{ "jingdong_xxx_responce": { ... } }`；失败：`{ "error_response": {"code":"...", "zh_desc":"...", "en_desc":"..."} }` `*` |
| 沙箱 | 有测试环境 `*`，**三平台里唯一能提前真联调的** |

#### J-A1 OAuth 换 token

| 入参 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `grant_type` | string | 是 | `authorization_code` / `refresh_token` |
| `client_id` | string | 是 | 即 `app_key` |
| `client_secret` | string | 是 | 即 `app_secret` |
| `code` | string | 条件 | `authorization_code` 时必填 |
| `refresh_token` | string | 条件 | `refresh_token` 时必填 |
| `redirect_uri` | string | 否 | 与申请时一致 |

| 出参 | 类型 | 说明 |
| --- | --- | --- |
| `access_token` | string | 业务凭证，有效期约 1 年 `*` |
| `refresh_token` | string | 续期凭证 |
| `expires_in` | number | 秒 |
| `scope` | string | 权限范围 |

> **与小红书/抖音的关键差异**：京东 token 是**长寿命**的（年级别），
> 续期压力小，但**一旦失效影响面大**（必须重新走店铺授权）。
> 中台巡检策略要区别对待：小红书/抖音按"周"巡检，京东按"月"巡检 + 失效立即告警。

### 3.2 商品管理

| 接口 | 功能 | 关键入参（中台侧来源） | 关键出参 | 错误码 |
| --- | --- | --- | --- | --- |

## 4. 天猫（淘宝开放平台）

### 4.1 框架层：网关 / 签名 / 授权

| 项 | 值 |
| --- | --- |
| 正式网关 | `https://eco.taobao.com/router/rest`（另有 `gw.api.taobao.com`） `*` |
| 沙箱网关 | `https://gw.api.tbsandbox.com/router/rest` `*` |
| 授权 | `https://oauth.taobao.com/authorize` → `https://oauth.taobao.com/token` |
| 请求方式 | POST / GET，业务参数**平铺**（不像抖音/京东塞进 JSON 串） |
| 公共参数 | `method`、`app_key`、`session`（**不是 access_token**）、`timestamp`（`yyyy-MM-dd HH:mm:ss`）、`format=json`、`v=2.0`、`sign_method`、`sign`、`partner_id` |
| 签名规则 | 按 key 升序拼 `k + v`（**不含 `=` 和 `&`**），首尾拼 `app_secret`，MD5 后转**大写** |
| 响应壳 | 成功：`{ "xxx_response": { ... } }`；失败：`{ "error_response": {"code":..., "msg":..., "sub_code":"isv.*", "sub_msg":"..."} }` |
| 沙箱 | 有沙箱环境 `*`，可提前联调 |
| 特色 | 有 **API 权限点体系**（免费/收费/需申请），且**调用量按次计费**，流控按 `app_key` + 接口 |

> **`session` 而不是 `access_token`**：中台适配层要用统一的 `token` 概念封装，
> 各平台字段名差异只在客户端内部消化（见实施方案 §2 的 `AbstractTokenStore`）。

> ① `props` 是**字符串拼接**（`pid:vid;pid:vid`），不是 JSON——和现有 `attrs`（`attr_key`/`attr_value`）
> 之间的转换要专门写适配函数 + 单元测试；
> ② 商品与 SKU 分离，且 SKU 的 `properties` 必须是商品 `props` 的**子集**，顺序敏感；
> ③ 大量接口有 `fields` 必填参数，**不传就返回极其精简的结构**（常见踩坑）；
> ④ 电话/资质/售后等类目专属必填项差异极大，**必须按类目分别回归**。

### 6.1 标题（与现有双平台方案的冲突预警）

`huopai_adapter.py:304` `WECHAT_TITLE_MAX=58`、`:309` `XHS_TITLE_MAX=30`，标题由 `enrich_titles(rows)`
按商品编码统一生成，且**两个平台的品名永不丢**、挤字段顺序固定。

接三个新平台后会出现**三个新问题**，必须在实施方案里排期：

1. **模板数量翻倍**：现有 `enrich_titles` 是双平台模板，要扩成 5 平台，`huopai_adapter.HEADERS:57`
   的「微信标题/小红书标题」两列要加三列，前端审核抽屉的标题编辑区也要加。
2. **重名风险放大**：现有结论是「同系列+色调+形状+品名的不同设计款在货盘里没有可写进标题的区分字段」，
   微信 151/250 会因重名被拒。多接 3 个平台后，**每个平台的拒单数几乎独立累加**
   （因为各平台的重名校验是独立的），这会把运营的失败清单从"百级"推到"数百级"。
   → 建议在开工前先按《新增店铺接入SOP》的口径确认：是否统一采用「标题加回 克拉+净度+镶嵌方式」
   方案（实测可把失败数压到 54/250 量级），或实现曾被删除的「款式名人工区分表」。
3. **长度上限不同**：需新增 `DOUYIN_TITLE_MAX` / `JD_TITLE_MAX` / `TMALL_TITLE_MAX` 常量，
   并让 `enrich_titles` 按平台循环生成，而不是 `if/else` 两分支。

> 这一节是本次接入**最容易被低估的工作量**：标题不是"加三列"，而是把一个双平台函数重构成
> N 平台 + N 套裁剪优先级。建议单独立项，不要和新平台客户端开发混在一起。

## 8. 结论：三个平台能不能在无软著阶段开工

| 工作项 | 现在能不能做 | 说明 |
| --- | --- | --- |
| 中台侧抽象重构（适配器注册表） | **能** | 不依赖任何平台凭证，先做收益最大 |
| 中台侧规范模型扩展（标题列、类目别名、店铺参数） | **能** | 纯本地改造 |
| `store` 客户端骨架（签名 + 请求壳 + 错误归一化） | **能** | 签名算法是公开的，可先写 + 单测 |
| 前端平台选项与审核抽屉 | **能** | 用 mock 数据驱动 |
| 真实接口联调 | **不能** | 等软著 → 权限点 → 文档/沙箱 |
| 订单/数据/营销模块 | **能设计、能落表** | 数据靠 mock 灌，接口后接 |

> 这正是实施方案中「模拟数据与真实接口切换机制」必须做扎实的原因：
> **在没有真接口的情况下，业务代码要能完整跑通并进入联调节奏**，否则软著下来后还要从零开发。
