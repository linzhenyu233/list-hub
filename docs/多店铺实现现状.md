## 1. 配置：一个 shop = 一个运营单元（同时含双平台）

`shops.json`（项目根，已 gitignore；模板见 `shops.example.json`）：

```
{
  "version": 1,
  "default_operator": "运营",
  "shops": [{
    "shop_id": "zuanshishijia",        // 小写字母/数字/下划线，启用后不要再改（数据库按它归档）
    "name": "钻石世家",                 // 前端展示名
    "enabled": true,                   // false：不出现在 GET /shops、worker 不领任务
    "is_default": true,                // 只能有一个；不写则取第一家 enabled 店
    "wechat": { "appid": "${WX_APPID}", "secret": "${WX_SECRET}",
                "brand_id": "...", "freight_template_id": "...", "after_sale_address_id": "..." },
    "xhs":    { "app_id": "${XHS_APP_ID}", "app_secret": "${XHS_APP_SECRET}",
                "access_token": "", "refresh_token": "",
                "brand_id": "...", "category_id": "...",
                "shipping_template_id": "...", "logistics_plan_id": "..." },
    "image_root": "\\\\192.168.10.250\\...\\SHINING HOUSE培育钻",
    "remark": "备注（后台店铺名、归属验证锚点商品 ID）"
  }]
}
```

- **密钥只写 `${环境变量}` 占位**，真实值留在 `.env` / Windows 用户环境变量；`runtime_config.load_project_env()` 先读用户环境变量、`.env` 再兜底。
- 平台是否可用：有 `wechat.appid` / `xhs.app_id` 即视为该平台已配置。
- 无 `shops.json` 时自动合成默认店 `shop_id = "default"`，行为与改造前单店完全一致（回滚手段）。
- `enabled=false` 的店也**可以先完成小红书授权**（`get_access_token.py` 用 `get_shop` 而非 `resolve`）。

当前配置的两家店：`zuanshishijia`（钻石世家，微信+小红书，默认店）、`xianshangmaodedian`（喜安商贸的店，仅小红书）。

## 2. 请求上下文与前端

- 请求头 `X-Shop-Id`（缺省回退默认店）、`X-Operator`（前端 `encodeURIComponent`，中台 `unquote` 还原）。
- 前端只有一个店铺选择器（**不是**方案稿里的"微信/小红书各选一个"）：`frontend/src/shopContext.js` 模块级 `ref` + localStorage，`api.js`/`xhsApi.js`/`bulkApi.js` 三个 axios 实例在请求拦截器统一注入。
- 浏览器自己发起的请求（`<img>`）带不了自定义头，用 `?shop_id=` 传店（例：`/images/preview`）。
- 切店后各面板按 `:key="...-${currentShopId}"` 强制重建（`KeepAlive` 内），避免残留上一家店的列表/分页状态。

## 3. 数据隔离

| 表 | 隔离方式 |
| --- | --- |
| `batches` | `shop_id` + `operator` + `revision` |
| `publish_jobs` | `shop_id` + `operator` |
| `publish_items` | `shop_id`（冗余，领任务 SQL 必须带） |
| `category_aliases` | `UNIQUE(shop_id, internal_category)`（老库已重建表） |
| `image_upload_cache` | `PRIMARY KEY(shop_id, platform, source_hash)`（老库已重建表，**图片不串店的关键**） |

- `batches.revision`：三个改写 `rows_json`/`mappings_json` 的接口（`PUT /import/{id}/items`、`PUT /import/{id}/mappings`、`POST /batches/{id}/images/scan`）各自 `revision+1`；`get_batch_cached()` 命中后再比一次 revision，**跨进程**（API 改映射 → worker 发品）立即生效，不再受 60 秒 TTL 影响。
- 迁移：`db()` 内固定顺序 `建表 → 补列(priority/shop_id/operator/revision) → 重建唯一约束表 → 历史数据归属 → 建索引`，幂等。
- 迁移前备份：`bulk_api/backups/bulk_catalog_pre_multishop_<时间戳>.sqlite3`（含 `-wal`/`-shm`）。
- 历史数据回填的 shop_id 记在 `_meta.legacy_shop_id`；配置里默认店改名后会自动跟迁（仅当目标店名下无数据）。

### P6 中发现并修复的 bug

- **未知 shop_id 返回 500**：`bulk_api.py` 的 `_current_shop_id()` 只取请求头、不做存在性校验，下游调 `shop_registry.image_root_for()` 等函数时未知店抛 `ValueError` → FastAPI 转成 500。修复：在 `_current_shop_id` 里调用 `_verify_shop` 统一转 400（微信/小红书服务原先已是 400，三服务行为对齐）。

## 5. 运维要点

- 端口：微信 `8000` / 小红书 `8010` / 中台 `8020` / 前端 `5173`。
- Worker：`bulk_worker.py` 启动时按 `(店铺 × 平台)` 起线程池（`BULK_WORKERS_PER_SHOP`，默认 6）。**新启用店铺必须重启 worker**，否则没有线程领它的任务。
- **改 `shops.json` / `.env` 后必须重启对应服务**（均无 `--reload`）。
- 日志：`bulk_api/_svc.out|_svc.err`、`bulk_api/_worker.out|_worker.err`、`xhs/_svc.*`、`wechat/_svc.*`（被 `.gitignore` 的 `*.out`/`*.err` 覆盖）。
- 小红书 token：按店存 `xhs/tokens/<shop_id>.json`；首次授权 `python xhs/get_access_token.py --shop <shop_id>`；巡检 `GET :8010/token/info`。**不要在项目根再生成 `token_store.json`**（会被当作"单店遗留"复制给默认店，造成串店）。
- 单店回滚：删除 `shops.json` 并重启全部服务。

## 6. 2026-09-16 双店联调结论（已实测）

- **隔离**：`GET /shops` 只列启用店；数据按店过滤；无头回退默认店；停用/未知店被拒（平台服务 `400 店铺已停用`）；同一张图在两店上传得到**不同素材 ID**。
- **新店真实发布成功**：货盘直读导入（560 行 / 250 商品 / 0 错误）→ 图片扫描（1-3 月，91 个商品匹配）→ 写入映射 → 发布 → 平台商品 `6aaa1796202ba2001524172a`（`ZDR01139-安宁`，小红书草稿）。
  归属验证：同一商品 ID 用老店身份查询返回 `-5000500 商品不属于该商家`；新店商品数 2→3，老店仍 151。
- **踩到的坑（已修）**：`batches` 批次缓存原先只有进程内失效 + 60 秒 TTL，API 改完映射、worker 是另一个进程，立刻重试会用旧映射 → 已改为按 `revision` 判新旧（提交 `6a587cd`）。
- **注意**：**运费模板 / 物流方案 ID 是分店的**，不能把 A 店的映射（或类目别名）直接复制给 B 店，否则平台报 `-5000500 运费模版(...)不存在`。前端批量发布流程是按当前店实时拉取，正常不会踩。
